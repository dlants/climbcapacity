# MongoDB Usage Analysis for ClimbCapacity

## Overview

ClimbCapacity is a climbing performance tracking application that uses MongoDB as its primary data store. The database architecture is designed around storing user climbing performance snapshots with complex measure data, handling authentication, and providing querying capabilities for performance analysis.

## Collections and Data Models

### 1. `snapshots` Collection

**Primary collection for climbing performance data**

**Schema (SnapshotDoc):**

```typescript
{
  _id: mongodb.ObjectId;
  userId: string;
  measures: {
    [measureId: MeasureId]: UnitValue;  // User-entered data with units
  };
  normedMeasures: NormedMeasure[];      // Normalized for indexing/querying
  createdAt: Date;
  lastUpdated: Date;
  importSource?: Dataset;  // "climbharder" | "powercompany" | undefined
}
```

**NormedMeasure Structure:**

```typescript
{
  measureId: MeasureId;
  value: number; // Converted to standard unit (kg, meters, IRCRA grades, etc.)
}
```

**Indexes:**

- `{ userId: 1, createdAt: -1 }` - For user snapshot retrieval
- `{ normedMeasures: 1 }` - For measure-based queries

### 2. `users` Collection

**User authentication records**

**Schema (UserDoc):**

```typescript
{
  _id: string; // Generated by Lucia auth
  email: string;
}
```

### 3. `sessions` Collection

**User session data (managed by Lucia)**

**Schema (SessionDoc):**

```typescript
{
  _id: string;
  expires_at: Date;
  user_id: string;
}
```

### 4. `magicLinks` Collection

**Temporary authentication tokens**

**Schema (MagicLinkDoc):**

```typescript
{
  code: string;
  userId: string;
  email: string;
  expiresAt: Date; // 15 minute expiration
}
```

### 5. `measureStats` Collection

**Aggregated statistics for measures (single document)**

**Schema (MeasureStatsDoc):**

```typescript
{
  stats: {
    [measureId: MeasureId]: number;  // Count of snapshots with this measure
  };
}
```

## Complex Query Patterns

### 1. Measure Range Queries

**Most complex querying involves the `normedMeasures` array:**

```typescript
// Example: Find all snapshots with weight between 65-75kg
{
  normedMeasures: {
    $elemMatch: {
      measureId: "weight",
      value: { $gte: 65, $lte: 75 }
    }
  }
}
```

### 2. Multi-Measure Queries

**Requires multiple `$elemMatch` conditions in `$and` array:**

```typescript
{
  $and: [
    {
      normedMeasures: {
        $elemMatch: { measureId: "weight", value: { $gte: 65, $lte: 75 } },
      },
    },
    {
      normedMeasures: {
        $elemMatch: { measureId: "height", value: { $gte: 1.7, $lte: 1.8 } },
      },
    },
  ];
}
```

### 3. Dataset Filtering

**Complex OR logic for including/excluding datasets:**

```typescript
{
  $or: [
    { importSource: { $in: ["climbharder"] } }, // Selected datasets
    { importSource: { $exists: false } }, // User-created snapshots
  ];
}
```

### 4. Measure Update Operations

**Uses MongoDB aggregation pipeline for atomic updates:**

```typescript
[
  {
    $set: {
      "measures.weight": { value: 70, unit: "kg" },
      normedMeasures: {
        $concatArrays: [
          {
            $filter: {
              input: "$normedMeasures",
              cond: { $not: { $in: ["$$this.measureId", ["weight"]] } },
            },
          },
          [{ measureId: "weight", value: 70 }],
        ],
      },
    },
  },
  { $unset: ["measures.deletedMeasure"] }, // Optional unset stage
];
```

## Authentication and Session Management

### Magic Link Flow

1. User requests login with email
2. Rate limiting: 5/hour per IP, 3/hour per email
3. Magic link generated with 16-character code, 15-minute expiration
4. Email sent via Resend API
5. Code verification creates new session, invalidates old ones
6. Session managed by Lucia with MongoDB adapter

### Session Security

- CSRF protection via origin/host header verification
- Secure cookies in production
- Session invalidation on login/logout
- Background cleanup of expired sessions

## Data Processing and Normalization

### Unit Conversion System

**Complex unit system with 20+ unit types:**

- **Physical units**: kg, lb, m, cm, inch, etc.
- **Climbing grades**: V-scale, Font, French Sport, YDS, Ewbank → IRCRA
- **Categorical**: sex-at-birth, training levels
- **Time**: seconds, years, months

**Two-way conversion:**

- `convertToStandardUnit()` - For storage/querying
- `convertToTargetUnit()` - For display

### Measure System

**Hierarchical measure generation:**

- 200+ measure types generated from base classes
- Parameterized measures (e.g., "maxhang:20mm:openhand")
- Type categories: performance, anthro, input, training
- Locale-specific defaults and ranges

## Aggregation and Statistics

### Measure Statistics Generation

**Single-pass aggregation over all snapshots:**

```typescript
// Counts occurrence of each measure across all snapshots
const measureStats = {};
for (const snapshot of allSnapshots) {
  for (const measureId in snapshot.measures) {
    measureStats[measureId] = (measureStats[measureId] || 0) + 1;
  }
}
```

**Challenges for MeiliSearch migration:**

- Single document updated with all statistics
- Requires full scan of snapshot collection
- Used for query result ranking/filtering

## Query Performance Considerations

### Current Optimization Strategies

1. **Compound indexes** on userId + createdAt for user queries
2. **Array indexing** on normedMeasures for measure queries
3. **Data duplication** - measures stored in both original and normalized forms
4. **Caching** - measure stats cached for 1 hour

### Performance Bottlenecks

1. **Complex array queries** - Multiple $elemMatch operations
2. **Dataset filtering** - OR logic with $exists checks
3. **Unit conversion** - Done at query time for display
4. **Aggregation pipeline updates** - Complex atomic operations

## Potential MeiliSearch Migration Challenges

### 1. Data Structure Challenges

- **Nested measure data** - MeiliSearch prefers flat document structure
- **Array queries** - `normedMeasures` array queries are core functionality
- **Multi-field filtering** - Complex AND/OR logic across measure combinations

### 2. Authentication Integration

- **Session management** - Would need to remain in MongoDB (Lucia dependency)
- **User data** - Simple user records could migrate, but session coupling

### 3. Real-time Updates

- **Atomic operations** - MeiliSearch doesn't support transactions
- **Concurrent updates** - Measure updates need atomic normedMeasures sync
- **Data consistency** - Original + normalized data must stay in sync

### 4. Query Complexity

- **Range queries** - MeiliSearch supports these well
- **Combined filters** - Complex measure combinations might be challenging
- **Dataset logic** - OR conditions with existence checks
- **Aggregations** - Statistics generation would need external processing

### 5. Unit System Integration

- **Normalization** - Would need to happen before indexing
- **Display conversion** - Post-query processing still needed
- **Search relevance** - MeiliSearch ranking might not align with measure-based relevance

## Recommendations for Migration Assessment

### Well-Suited for MeiliSearch

- **Text search** - User-friendly measure names, descriptions
- **Faceted search** - Dataset filtering, measure categories
- **Range filtering** - Measure value ranges
- **Performance** - Faster than complex MongoDB array queries

### Requires Careful Planning

- **Document flattening** - Restructure normedMeasures array
- **Hybrid approach** - Keep MongoDB for auth/sessions, MeiliSearch for search
- **Data synchronization** - Ensure consistency between systems
- **Query rewriting** - Translate complex MongoDB queries to MeiliSearch

### Potential Blockers

- **Atomic updates** - Complex measure update logic
- **Transaction requirements** - Multi-document consistency needs
- **Real-time statistics** - Aggregation pipeline replacement
- **Search relevance tuning** - May need significant ranking customization
